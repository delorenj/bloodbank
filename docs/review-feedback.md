# BB-67 · Holocene walkthrough feedback command boundary

This is the **Bloodbank source candidate**, not permission to enable Holocene's producer. `HOLOC-70` owns the preserved review, the frozen submission/outbox, explicit-Send click, retry scheduling, Candystore read projection and rendering in the **same revision**. Bloodbank owns this schema, the `bb-emit` feedback-only adapter, the opt-in gateway durable, native execution/capture and resulting lifecycle facts. No direct Holocene→Hermes call, second invocation command, Plannotator wakeup or automatic duplicate execution.

## Frozen row and producer

On an authenticated explicit Send, Holocene persists exactly one row first. Supply that persisted JSON row on stdin (or `--data`), including `createdAt` in addition to these wire fields:

`submissionId` (canonical UUID), `projectId` (`greeninbetween`), `revisionId` (64 lowercase hex characters), `artifactId`, `author`, `recipient` (`green-in-between-pm`), `note` (at most 4000 characters), `annotations` (1–500 saved `[id, version, author, kind, anchor, comment, updatedAt]` records), `digest`, `correlationId` (canonical UUID).

Annotations retain their own authors (not necessarily the submission author). Require unique nonempty IDs, integer versions ≥1, `kind` text/element, object anchors, nonblank comments ≤10000 characters, and RFC3339 `updatedAt`. The complete compact UTF-8 envelope is limited to 262144 bytes before any publish; an oversized saved row fails validation without truncation or dropping marks. Holocene must retain it and show the refusal. The installed gateway must retain at least this ingress cap; a changed cap needs a coordinated contract update.

`digest` is Holocene `freezeFeedback`'s SHA-256 of compact UTF-8 JSON `{"note":note,"annotations":[[id,version],...]}` in saved annotation order; it **does not** cryptographically bind every frozen field. Do not silently recalculate it from changed input. After save, never rewrite the row or its annotations to retry a delivery. A new review edit needs a new submission ID. The producer must also preserve the original `createdAt`; current delivery `state`, `stateDetail`, and `updatedAt` are intentionally excluded from the command. `createdAt` is envelope time; retries never use the retry wall clock. Extra mutable row fields are not on wire.

The Bloodbank adapter projects the row through `core.review_feedback.build_command` (invoked by `bb-emit --feedback-submission`). It derives stable UUIDv5 envelope ID and command ID from `urn:33god:review-feedback:<submissionId>`, a stable `review.feedback.send:<submissionId>` idempotency key, `correlationid = correlationId`, `causationid = submissionId`, `actor = {type:operator,agent_id:author}`, and the command subject `bloodbank.cmd.review.feedback.send`. The precise UUID derivation is implementation-defined; consumers must use the returned IDs instead of independently guessing them. Type is `bloodbank.review.feedback.send`, schema revision 1. The gateway rejects changed command bytes sharing an existing command ID. This is a local journal replay guarantee, **not** global exactly-once side effects or a JetStream deduplication-window promise.

On a deployed matching Bloodbank source, with **no** subscription yet enabled for a live review, Holocene can dry-run:

```sh
bb-emit --type bloodbank.review.feedback.send --feedback-submission --check < frozen-row.json
```

The dry run validates both the naming contract and the JSON schema and prints only IDs/lineage; it does not publish. Only after reviewed install, profile/registry preflight and coordinated Holocene enablement may its outbox use the same invocation **without `--check`**. `bb-emit` then requires a JetStream `BLOODBANK_COMMANDS` PubAck (`stream`,`seq`), not a core NATS PONG. Exit 0 and that receipt prove the command was stored in the stream, **not** that Hermes executed or answered. An error, timeout or missing PubAck exits nonzero regardless of `--strict` and is `uncertain`, not a dropped command or a reason to blindly execute another command. The producer reconciles by submission/command identity, retains the frozen row and uses bounded retry; a publish-before-receipt fault may already have accepted the bytes. The generic `bb-emit` path retains its old behavior but explicitly refuses feedback without `--feedback-submission`.

## Gateway and answer

Opt-in `bloodbank.extra.feedback: {enabled: true}` configures a dedicated `bloodbank-hermes-gateway-feedback` pull consumer on the feedback subject. It shares the gateway's private durable execution journal and result outbox; no other lane's durable/slots are repurposed. Do **not** enable this until the candidate is reviewed and installed. Require the registry target `green-in-between-pm` eligible, its profile installed, and resolved profile exactly `green-in-between-pm`. Unknown/changed routes fail closed with a durable queued→failed pre-start closure; no fallback to `bloodbank-pm` or an arbitrary direct profile. The feedback lane forbids `shutdown_interrupt: retry`. It builds one internal Hermes invocation, thread `review:<projectId>:<revisionId>`, logical turn/command ID joined to the original submission, and sends the frozen note/anchors as untrusted content; it never publishes a second command. For feedback turns the `conversation.turn.started` fact omits `prompt_text`, avoiding raw review content in that lifecycle fact. Native session/turn IDs come only from actual capture, not synthetic logical IDs.

The feedback route consults registry eligibility independently of `target_profiles` and direct-profile overrides, again after lifecycle publication before dispatch. Generic invocation lanes retain their documented override semantics. A command-scoped Linux file-description lock beside the private journal excludes other adapters in the same PID as well as other processes. Hold it through dispatch, capture and processing reconciliation; a live owner cannot be superseded by a timer or another adapter's empty in-memory map. Process exit releases the lock: an abandoned pending claim can run, but a previously started claim closes uncertain, never automatic execution replay. Do not unlink the lock files or move a live journal/lock directory.

On the final broker delivery, a registry outage or queued-publication fault closes durably with `feedback_delivery_exhausted`. An unstarted claim records only queued→failed, not a fabricated started/turn fact; an already started claim remains uncertain. A private additive journal receipt tracks completed feedback result publication (including exhausted closures). Connection and feedback fetch-cycle reconciliation replay up to 100 stored deterministic result batches per cycle independently of another command delivery and mark the receipt only after all PubAcks. Publication may repeat; consumers must deduplicate by fact ID. This is not globally exactly-once transport or execution.

A queued row waiting for a slot may be retried; after a durable `started` row exists, a restarted gateway without durable native capture cannot safely infer whether Hermes ran. It closes that command as `agent.invocation.failed` `error_code=feedback_execution_uncertain`, which Holocene must display as uncertain and escalate/manual reconcile **without automatic replay**. When native capture and the processing result survive, the existing gateway finalizer and result outbox store the full final assistant body before PubAck/command ACK; failures after that replay stored event bytes without a second turn. If only native capture survived and the processing callback did not, the existing gateway closes `processing_outcome_unknown`, preserves the capture privately and does **not** publish it as an answer; Holocene displays uncertain. `agent.invocation.completed` alone is not an answer. A feedback turn that finishes without a qualified nonempty native final body and native IDs closes `feedback_final_answer_missing` instead of success; saved content remains intact.

Holocene must consume **trusted durable Candystore** lifecycle facts, not UI-local fabricated facts. `core.review_feedback.evidence_state(command,event,profile=...)` is a validation/join helper, not an authentication or persistence API. Join the exact `lane=feedback`, original `command_type`, complete-envelope `command_digest` (gateway compact sorted-key JSON SHA-256, **not** the annotation digest), `command_event_id`, `command_causationid` and `issuer` on every feedback fact. Validate the deterministic fact/message ID, turn ordering key and phase-specific lifecycle causation with the helper; copied review context on a batch/interactive answer is not feedback evidence. Also join original command ID, idempotency key, correlation ID, target and resolved profile, logical thread/turn, review context (`submissionId`, project/revision/artifact/digest/recipient), gateway actor/source/service/producer and original issuer. Only a `bloodbank.conversation.message.appended` fact with `role=assistant`, `final_answer=true`, nonempty nonsilent exact text, original command causation and **observed** nonempty `native_session_id` and `native_turn_id` can move the same review to `answered`; retain the fact ID, Candystore cursor and exact body privately. An unrelated profile, synthetic text, interim progress or turn completion cannot do so. Facts may arrive out of order; persist a monotone projection so a late queued/started fact cannot regress answered or failed.

| Holocene state | Required evidence |
| --- | --- |
| `saved` | Frozen row exists; no publication claim. |
| `queued` | PubAck confirms stream acceptance or a matching gateway `invocation.queued` durable fact; distinguish the two receipts. |
| `published` | Persisted stream PubAck and its sequence; execution still unproven. |
| `uncertain` | No confirmed PubAck after attempted publish, or `feedback_execution_uncertain`/`processing_outcome_unknown`/`feedback_delivery_exhausted` failure. Preserve command identity for manual reconciliation. |
| `answered` | Matching durable native final-answer fact joined to original row and revision; immutable answer and provenance shown in the same review. |
| `failed` | Matching terminal gateway failure with no matching final-answer fact; classify timeout/refusal separately. |

A `running` display can be derived from a matching `invocation.started` fact, but it is not an outbox state. The read-side owns ordering, access control and terminal precedence; this mapping does not make a UI decision by itself. `failed` and `uncertain` need an explicit owner response before resubmission, not a new UUID behind the operator's back.

## Acceptance still outside this candidate

Independent spec and quality review, installation of schema/CLI/gateway in the **serving** environment, configuration of the opt-in durable, coordinated Holocene outbox producer/UI, and one bounded real explicit Send to `green-in-between-pm` remain. Verify the submitted row survives API restart; inject save-before-send, crash-before-publish, publish-before-receipt, gateway claim/start/capture/publish/ACK faults. Show one real native answer joined to command and original review, a durable Candystore row and that answer rendered in the same review. Disposable fixtures exercise source mechanics but are **not** the real pilot or durable arrival evidence. Do not deploy/restart a fleet gateway or publish live feedback from this candidate handback.
